## Findings

### GAMLIB-TLS-PROXY-NOVERIFY
- **Severity:** medium
- **Confidence:** high
- **Where:** `src/gam/atom/service.py:82`, `src/gam/atom/http.py:247-255`, `src/gam/atom/http_core.py:564-572`

`AtomService` defaults to `atom.http.ProxiedHttpClient`:

```82:82:src/gam/atom/service.py
        self.http_client = http_client or atom.http.ProxiedHttpClient()
```

On the HTTPS proxy path that client builds a context that does not verify the server:

```247:255:src/gam/atom/http.py
                # Trivial setup for ssl socket.
                sslobj = None
                if ssl_imported:
                    context = ssl.SSLContext(ssl.PROTOCOL_TLS)
                    context.minimum_version = ssl.TLSVersion.TLSv1_2
                    sslobj = context.wrap_socket(p_sock, server_hostname=url.host)
                else:
                    sock_ssl = socket.ssl(p_sock, None, None)
```

The same pattern is in `src/gam/atom/http_core.py:564-572`. `GDataService` (`src/gam/gdata/service.py:216-223`) uses this client for domain shared contacts and the Email Audit API. Those requests carry `Authorization`.

`ssl.SSLContext(ssl.PROTOCOL_TLS)` on this machine's Python 3.15 leaves `verify_mode` at `CERT_NONE` (0), `check_hostname` false, and the CA list empty. Setting `minimum_version` to TLS 1.2 does not change that. `server_hostname` only sends SNI. The context never calls `load_verify_locations` or `load_default_certs`, so `cacerts.pem` is not used here. The direct (no-proxy) branch uses `http.client.HTTPSConnection`, which uses `create_default_context` and does verify.

The commented-out `sendall` / `recv` lines are a Python 3 port of upstream gdata. Upstream `socket.ssl(p_sock, None, None)` also did not verify. This port added SNI and a TLS 1.2 floor and still does not check the certificate. It is a maintained verification gap, not a hardcoded callback host.

The deprecated twin in `src/gam/atom/service.py:413-414` still calls `socket.ssl`. That attribute is gone in Python 3, so that function dies before connecting.

**Confirm:** with `https_proxy` set, a domain shared-contacts or email-audit call should complete TLS against a forged certificate. Check `src/gam/__init__.py` (outside this scope) to see whether those commands still construct `gdata` clients or have moved to `google-api-python-client`.

### YUBIKEY-DEFAULT-MGMT-KEY
- **Severity:** low
- **Confidence:** high
- **Where:** `src/gam/gamlib/yubikey.py:143-169`

`reset_piv` wipes PIV, sets a new PIN and PUK, then authenticates with Yubico's public default management key and never replaces it:

```143:156:src/gam/gamlib/yubikey.py
        piv.reset()
        rnd = SystemRandom()
        new_puk = ''.join(rnd.choice(PIN_PUK_CHARS) for _ in range(8))
        new_pin = ''.join(rnd.choice(PIN_PUK_CHARS) for _ in range(8))
        piv.change_puk('12345678', new_puk)
        piv.change_pin('123456', new_pin)
        writeStdout(Msg.YUBIKEY_PIN_SET_TO.format(new_pin))
        piv.authenticate(piv.management_key_type, DEFAULT_MANAGEMENT_KEY)
        piv.verify_pin(new_pin)
        writeStdout(Msg.YUBIKEY_GENERATING_NONEXPORTABLE_PRIVATE_KEY)
        pubkey = piv.generate_key(SLOT.AUTHENTICATION,
                                  KEY_TYPE.RSA2048,
                                  PIN_POLICY.ALWAYS,
                                  TOUCH_POLICY.NEVER)
```

The signing key is generated non-exportable with `PIN_POLICY.ALWAYS` and `TOUCH_POLICY.NEVER`. Signing still requires the PIN (`sign` at lines 188-192, PKCS#1 v1.5 + SHA-256, which is what Google RS256 service-account JWTs use). Anyone who can touch the key can authenticate management with the published default and replace the slot. The new PIN is printed to stdout so the admin can record it.

**Confirm:** after this reset, PIV management auth with Yubico's default management key (`010203…1d`) should succeed.

### CACERTS-SSLCOM-CLIENT-ROOTS
- **Severity:** info
- **Confidence:** high that these are the named public roots; medium on why they are in the TLS bundle
- **Where:** `src/gam/cacerts.pem:2-6` and the comment blocks for certificates 22 and 23

```2:6:src/gam/cacerts.pem
# This is a custom certificate authority bundle for GAM
# It's composed of Let's Encrypt Root CAs and Google's
# certificate bundle. This should be the minimal list of
# CAs required to talk to Google and Github.
```

The file has 23 certificates. All are self-signed `CA:TRUE`. Subjects are ISRG, Google Trust Services, GlobalSign, DigiCert, GoDaddy, Starfield, COMODO, USERTrust, and SSL.com. No private or unknown organization. SHA-256 fingerprints match the comments in the file. GoDaddy and Starfield G2 still have serial `0` (the cryptography warning); that is those roots, not a new certificate.

The last two are `SSL.com Client RSA Root CA 2022` and `SSL.com Client ECC Root CA 2022` (SHA-256 `1d4ca4a2ab21d0093659804fc0eb2175a617279b56a2475245c9517afeb59153` and `ad7dd58d03aedb22a30b5084394920ce12230c2d8017ad9b81ab04079bdd026b`). They have no extended key usage. A trust anchor with no EKU can anchor a server certificate. The header does not mention them.

**Confirm:** compare those fingerprints with SSL.com's published Client RSA/ECC Root CA 2022, and with the commit that added them (CSE or client-certificate use versus TLS server trust).
